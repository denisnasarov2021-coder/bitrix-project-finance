# Контур проектов · Финансы Битрикс24

[![Автоматические проверки](https://github.com/denisnasarov2021-coder/bitrix-project-finance/actions/workflows/check.yml/badge.svg)](https://github.com/denisnasarov2021-coder/bitrix-project-finance/actions/workflows/check.yml)

Веб-приложение для совместного ручного учёта доходов и расходов по проектам. Подготовлено как тестовое задание для аналитика сопровождения и развития действующих порталов Битрикс24.

**Быстрая проверка:** Node.js 24 LTS, затем две команды из каталога проекта:

```bash
npm ci
npm run demo
```

Откройте адрес, который напечатает Vite, обычно `http://localhost:5173`. Первый запуск применит миграции к локальной SQLite/D1 и при первом обращении создаст демонстрационные данные. Аккаунты Cloudflare и Битрикс24 для локальной демонстрации не нужны. Интернет необходим для установки npm-зависимостей. Деморежим запускается на loopback-интерфейсе компьютера; для совместной работы нужен один общий сервер.

## Что реализовано

- Создание проектов, название клиента и описание работ.
- Ручное добавление, изменение и удаление доходов/расходов; дата оплаты и комментарий.
- Статья дохода «Оплата клиента» и пять обязательных расходов: внешние программисты, внутренние программисты, расходы на ИИ, аренда сервера, дивиденды.
- Добавление собственных статей доходов и расходов. Дубли по типу и названию, включая регистр, запрещены.
- Добавление сотрудников к проектам с ролями руководителя, редактора и наблюдателя.
- Доходы, расходы, прибыль, рентабельность; детализация проекта, период и структура расходов.
- Общая серверная база. Изменения других участников видны при обновлении и автоматически каждые 30 секунд.
- Серверная проверка прав; история с автором и значениями до/после; мягкое удаление.
- Защита от повторного сохранения операции и от потери одновременных правок.
- Встраивание в меню облачного Битрикс24: страницы `/bitrix`, `/install`, SDK, проверка пользователя через REST и загрузка сотрудников по страницам.

Приложение хранит собственные проекты и операции. Оно не меняет существующие лиды, сделки, воронки и роботов портала. Это соответствует подходу сопровождения: отдельный финансовый контур, понятные права, проверка изменений и документация.

## Как проверить за пять минут

1. В режиме «Анна · администратор» откройте «CRM для „Вектор“».
2. Сверьте исходные цифры: доходы **300 000 ₽**, расходы **155 000 ₽**, прибыль **145 000 ₽**, рентабельность **48,3%**. До дивидендов прибыль **165 000 ₽**.
3. Добавьте доход **10 000 ₽**. Доходы станут **310 000 ₽**, прибыль **155 000 ₽**, рентабельность **50%**.
4. Создайте расходную статью «Дизайн» и расход **5 000 ₽**. Прибыль станет **150 000 ₽**, рентабельность **48,4%**.
5. Во вкладке «Команда» добавьте Игоря редактором. В другой вкладке выберите Игоря и откройте тот же проект: данные общие.
6. Переключитесь на Елену: в исходном проекте «CRM для „Вектор“» она наблюдатель и не может менять операции. Доступ к проекту «Поддержка „Альфа“» изначально отсутствует.
7. Откройте одну операцию на редактирование в двух вкладках. Сохраните первую, затем вторую: второе сохранение получит сообщение о конфликте. Закройте форму, обновите список и откройте актуальную запись.
8. Удалите тестовый расход. Прибыль пересчитается, удаление останется в истории.

Демонстрационный переключатель имитирует четыре учётные записи и предназначен только для учебных данных. В рабочем режиме его нет; отправленный `X-Demo-User` не предоставляет доступ. Демо и рабочий портал разделены идентификатором пространства данных.

## Финансовая модель

Один проект ведётся в рублях; учитываются фактически внесённые оплаты. Даты периода включаются с обеих сторон. Пустая граница означает отсутствие ограничения.

| Показатель | Правило |
|---|---|
| Доходы | Сумма действующих операций статей доходов |
| Расходы | Сумма всех действующих расходов, включая дивиденды |
| Прибыль | Доходы − расходы |
| Рентабельность продаж | Прибыль / доходы × 100% |
| Прибыль до дивидендов | Прибыль + дивиденды |
| Доходы равны нулю | Рентабельность не определена; в интерфейсе «—» |
| Портфель проектов | Сначала суммируются доходы/расходы, затем рассчитывается процент |

**Решение по дивидендам:** в задании они прямо перечислены как расход. Поэтому итоговая прибыль и рентабельность в этом приложении рассчитываются после них. Для интерпретации результата отдельно показана прибыль до дивидендов. Это управленческая модель по условиям задания, а не бухгалтерская отчётность по методу начисления.

Деньги хранятся целыми копейками. `12 500,50` и `12500.50` дают одинаковое значение `1250050`. Ноль, отрицательные суммы и более двух десятичных знаков отвергаются. Тип задаёт направление операции; отрицательные суммы не используются. Исправление ошибочной записи делается редактированием или удалением. Возвраты, НДС, валюты, плановые платежи и распределение общих затрат автоматически не рассчитываются.

## Роли

| Действие | Администратор приложения | Руководитель проекта | Редактор | Наблюдатель |
|---|---|---|---|---|
| Просмотр финансов | Все проекты | Свой проект | Свой проект | Свой проект |
| Добавление/изменение/удаление операций | Да | Да | Да | Нет |
| Состав команды и её роли | Да | Да | Нет | Нет |
| Создание статьи | Да | Да, общая для проектов | Нет | Нет |
| История изменений | Все проекты | Свой проект | Свой проект | Свой проект |

Любой авторизованный сотрудник может создать новый проект и становится его руководителем. Собственную роль в проекте нельзя удалить или понизить. Администратор приложения назначается серверной настройкой `BITRIX_ADMIN_IDS`, а не произвольным флагом из браузера.

## Подключение к Битрикс24

Пошаговая инструкция: [docs/BITRIX24.md](docs/BITRIX24.md).

Нужны общий сервер Cloudflare Worker + D1, HTTPS, доступ к локальным приложениям облачного портала и scope `user_basic` (или `user`). Коробочная редакция и произвольные домены требуют отдельной адаптации списка допустимых хостов.

**Статус проверки:** интеграционные тесты проверяют серверный адаптер с контролируемыми ответами REST. Установка на реальный портал и работа iframe с реальными сотрудниками ещё не проверялись: доступ к порталу в рамках задания не предоставлен.

Приватная демонстрационная ссылка в ChatGPT служит для ознакомления владельца. Она требует входа в ChatGPT и не заменяет внешний HTTPS-адрес, доступный iframe Битрикс24 и сотрудникам работодателя.

## Архитектура

| Часть | Назначение |
|---|---|
| React + TypeScript, Vinext/Vite | Интерфейс и сборка |
| Cloudflare Worker | HTTP API, проверка пользователя и прав |
| D1 / SQLite | Общие проекты, статьи, сотрудники, операции и история |
| Drizzle | Версионируемая схема и SQL-миграции |
| BX24 JS SDK + REST | Контекст портала, текущий пользователь, список сотрудников |

Основной код: `components/finance-app.tsx`, `lib/finance.ts`, `lib/server/api.ts`, `lib/server/auth.ts`. Схема находится в `db/schema.ts`, миграции в `drizzle/`. Подробности API и защиты данных: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Состояние проектов не сохраняется в `localStorage`. При перезапуске демо данные остаются в каталоге `.wrangler/state`. Не добавляйте этот каталог или `.dev.vars` в Git. Для чистого демо остановите сервер и удалите только локальный каталог `.wrangler/state` этой копии проекта: все данные этой локальной копии будут удалены. Затем запустите `npm run demo`.

## Проверки

```bash
npm run typecheck
npm test
npm run build
npm run test:build
```

Сборка использует bash из стандартного шаблона: Linux/macOS или Git Bash/WSL на Windows. Команда демонстрации написана на Node.js и не требует bash. Если локальный Node не поддерживает удаление TypeScript-типов при запуске тестов, используйте Node 24 LTS.

Финансовые тесты используют заранее рассчитанные ожидаемые значения. API-тесты вызывают настоящий обработчик с настоящей локальной D1 через Miniflare; база не подменяется объектом в памяти. Проверяются повторы записи, конфликт двух сотрудников, права на чужой проект, мягкое удаление, аудит, фильтрация пользователей и авторизация Битрикс24. Контролируемая подмена используется только для внешнего REST Битрикс24.

## Границы решения

Это работающее тестовое MVP для небольшой команды. Отчёт загружает операции доступных проектов целиком; до большого объёма данных нужны серверная агрегация и пагинация. Нет обмена с 1С, сопоставления с CRM-сделками, фонового импорта и платёжного календаря: ручной учёт является условием задачи. Авторизация проверяется через `user.current` при каждом API-запросе; при масштабировании следует добавить безопасный краткоживущий серверный кеш и контроль лимитов REST.

Ни демонстрационные значения, ни результаты тестов не являются данными реального клиента.
