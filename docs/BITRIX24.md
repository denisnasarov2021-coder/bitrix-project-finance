# Развёртывание и установка в Битрикс24

## 1. Проверить предпосылки

На первом созвоне уточнить облачную/коробочную редакцию, наличие доступа к локальным приложениям на тарифе, администратора портала, список пользователей и ответственного за финансовые правила. Здесь реализован вариант **облачного портала** с отдельной базой приложения. Существующие настройки CRM не меняются.

## 2. Поднять общий сервер

Локальное демо предназначено для проверки. Сотрудникам нужен один HTTPS-сервер с одной общей D1.

Приложение собирается в Cloudflare Worker. Для самостоятельного развёртывания нужны аккаунт Cloudflare, Wrangler из зависимостей и отдельная D1. Пример последовательности:

```bash
npx wrangler login
npx wrangler d1 create bitrix-project-finance
npm run build
```

Создайте `wrangler.production.jsonc` по примеру ниже. В `database_id` подставьте ID, который вернула команда создания D1. Впишите реальный домен вашего облачного портала и числовые ID администраторов приложения. Это **шаблон конфигурации**, а не готовые реквизиты.

```json
{
  "name": "bitrix-project-finance",
  "main": "dist/server/index.js",
  "compatibility_date": "2026-05-01",
  "compatibility_flags": ["nodejs_compat"],
  "assets": { "directory": "dist/client", "binding": "ASSETS" },
  "d1_databases": [{
    "binding": "DB",
    "database_name": "bitrix-project-finance",
    "database_id": "REPLACE_WITH_DATABASE_ID",
    "migrations_dir": "drizzle"
  }],
  "vars": {
    "APP_MODE": "bitrix",
    "BITRIX_DOMAIN": "your-company.bitrix24.ru",
    "BITRIX_ADMIN_IDS": "1,7"
  }
}
```

```bash
npx wrangler d1 migrations apply DB --remote --config wrangler.production.jsonc
npx wrangler deploy --config wrangler.production.jsonc
```

После успешной команды используйте напечатанный адрес Worker. Дальше он обозначен `https://APP_HOST`.

`APP_MODE=demo` нельзя использовать с настоящими финансовыми данными. При одновременных `APP_MODE=demo` и непустом `BITRIX_DOMAIN` сервер отказывает в работе. Если `APP_MODE` не задан, сервер требует авторизацию Битрикс24; анонимного перехода в демо нет.

Файлы окружения, данные `.wrangler`, токены и приватные ключи не коммитятся. В проекте нет клиентского секрета или общего вебхука администратора. Приложение не выполняет фоновые запросы от лица другого сотрудника.

## 3. Зарегистрировать локальное приложение

В портале администратор открывает **Приложения → Разработчикам → Другое → Локальное приложение**. Названия пунктов могут отличаться по интерфейсу портала.

| Поле | Значение |
|---|---|
| Тип | Серверное, с интерфейсом |
| Путь обработчика | `https://APP_HOST/bitrix` |
| Путь первоначальной установки | `https://APP_HOST/install` |
| Название пункта меню | Финансы проектов |
| Права приложения | Пользователи, базовые поля (`user_basic`), либо `user` |

Сохраните приложение и откройте страницу установки. Нажмите «Завершить установку». После `BX24.init` приложение проверяет пользователя через свой сервер; при успешной проверке вызывает `BX24.installFinish`.

В рабочем запуске Битрикс24 может отправить POST на `/bitrix`. Обработчик переводит его на страницу приложения, сохраняя только контекст SDK: `DOMAIN`, `PROTOCOL`, `LANG`, `APP_SID`. Токены из POST не попадают в URL. SDK получает актуальную авторизацию от родительского портала.

## 4. Добавить команду

Администратор приложения или руководитель создаёт проект. На вкладке «Команда» нажимает «Добавить сотрудника», затем «Обновить список из Битрикс24». Если пользователей более 50, продолжает кнопкой загрузки следующей страницы. Загрузка списка не выдаёт доступ к финансам: он появляется только после добавления сотрудника к проекту.

Роль `BITRIX_ADMIN_IDS` даёт доступ ко всем проектам приложения. Остальные роли назначаются отдельно в каждом проекте. Отображаемый выбор роли не заменяет серверную проверку.

## 5. Приёмка на тестовом портале

- Открыть приложение в iframe под двумя реальными сотрудниками.
- Создать проект и добавить второго сотрудника редактором.
- Внести сумму первым сотрудником и увидеть её вторым.
- Убедиться, что у наблюдателя нет прав записи, в том числе через прямой запрос API.
- Проверить загрузку следующих страниц сотрудников.
- Проверить обновление OAuth-токена после истечения срока.
- Проверить доступ из браузеров с ограничениями сторонних cookies. Приложение не зависит от собственных auth-cookies; OAuth-токен находится только в оперативной памяти вкладки.
- Проверить, что iframe допускается: Worker выставляет `frame-ancestors` для настроенного портала. Прокси перед Worker также не должен запрещать встраивание.
- Согласовать правила доходов, дивидендов и распределения общих расходов до ввода реальных данных.

Эти проверки на реальном портале остаются отдельным этапом: в среде подготовки задания доступа к порталу нет.
