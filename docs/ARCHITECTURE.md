# Устройство приложения

## Данные

| Таблица | Назначение и ограничения |
|---|---|
| tenants | Пространство demo или заданный сервером домен портала |
| users | Идентификатор сотрудника, имя, роль администратора; Bitrix ID хранится отдельно |
| projects | Название, клиент, описание, автор |
| members | Связь проект–сотрудник; уникальный составной ключ, роль в проекте |
| categories | Тип доход/расход; уникальные тип и нормализованное имя в пространстве |
| entries | Целые копейки, статья, проект, дата, авторы, версия, признак удаления |
| audit | Действие, автор, время, снимки до/после |

Внешние ключи не позволяют создать запись с несуществующей статьёй/проектом/автором. CHECK в базе ограничивает сумму, тип статьи и роли. Дополнительно API проверяет принадлежность сущностей к одному порталу. Глобальные ID генерируются UUID; исходные демо-ID имеют отдельный префикс.

Обновление состояния выполняется группой SELECT в D1 batch, чтобы показатели и список прав читались из согласованного состояния базы.

## Запросы

| Метод и путь | Назначение |
|---|---|
| GET `/api/config` | Только текущий режим, без финансовых данных |
| GET `/api/state` | Сотрудник и доступные ему проекты, операции, статьи, участники |
| POST `/api/projects` | Создать проект и назначить автора руководителем |
| POST `/api/categories` | Создать статью; руководитель/администратор |
| POST `/api/entries` | Создать операцию с UUID для защиты от повторной записи |
| PATCH `/api/entries/:id` | Обновить при совпадении версии |
| DELETE `/api/entries/:id` | Мягко удалить при совпадении версии |
| POST `/api/projects/:id/members` | Добавить сотрудника или изменить роль |
| DELETE `/api/projects/:id/members` | Удалить сотрудника из проекта |
| GET `/api/projects/:id/audit` | Последние 100 событий проекта |
| POST `/api/directory` | Получить следующую страницу активных сотрудников Битрикс24 |

Пример тела операции:

```json
{
  "id": "d6b827c6-ff25-41d9-a113-405d45a7fd7d",
  "projectId": "project-id-from-api",
  "categoryId": "category-id-from-api",
  "amount": "12500,50",
  "date": "2026-09-08",
  "note": "Настройка CRM"
}
```

Для PATCH дополнительно передаётся `version`. Тип операции определяется статьёй, поэтому несовпадение типа и статьи невозможно. Перенос существующей записи в другой проект через PATCH не предусмотрен.

## Совместная работа

1. **Повтор отправки.** Форма создаёт UUID при открытии. Повторный POST с тем же UUID и тем же содержимым возвращает ранее созданную операцию. Тот же UUID с другой суммой/автором/проектом возвращает 409.
2. **Одновременное редактирование.** UPDATE проверяет `WHERE version = :expected AND deleted_at IS NULL` и увеличивает версию. Факт изменения определяется `RETURNING id, version`, а не счётчиком затронутых строк: триггер аудита тоже пишет в базу.
3. **История.** INSERT/UPDATE-триггеры создают аудит в той же транзакции. Удаление меняет `deleted_at`; запись исключается из расчётов, но сохраняется в базе.
4. **Доступ.** Каждый запрос проверяет пользователя на сервере. Наличие кнопки или знания ID не предоставляет прав. После удаления участника последующие запросы закрываются; уже загруженную копию информации в браузере отозвать задним числом нельзя.
5. **Синхронизация.** Новые данные запрашиваются каждые 30 секунд, при возвращении во вкладку и кнопкой обновления. Это polling, а не WebSocket.

## Авторизация

В рабочем режиме сервер получает access token текущего пользователя в `Authorization: Bearer`. `user.current` вызывается исключительно на `BITRIX_DOMAIN`, заданном при развёртывании. Переданные клиентом domain, user ID, admin flag и demo header не используются для выдачи прав. URL произвольного сервера передать нельзя; перенаправления внешнего REST запрещены, задан таймаут.

Авторизованный сервером пользователь привязывается к пространству домена. Имя берётся из ответа REST; финансовые права берутся из таблицы участников и серверного списка администраторов. Токен не записывается в базу, localStorage, Git или логи. После 401 клиент обновляет его через SDK и делает одну повторную попытку. Неуспешная авторизация не изменяет данные.

API не использует auth-cookies. Изменения принимаются JSON-запросами; чужой Origin отвергается. SQL параметризован. Пользовательский текст выводится React как текст, без `dangerouslySetInnerHTML`. Ошибки не возвращают SQL или секреты. Для демонстрации на Sites действует внешняя приватность по владельцу; демонстрационный выбор сотрудника сам по себе механизмом безопасности не является.

## Эксплуатация и развитие

До использования реальных финансов нужна приёмка на портале, резервное копирование D1, закреплённый владелец прав и регламент изменений. Для большого объёма: серверная агрегация по периоду, страницы операций/истории, ограничение частоты запросов и наблюдаемость интеграции. Коробочные домены в текущий allowlist не входят.

Нет синхронизации с существующими группами/задачами Битрикс24: проект является отдельной сущностью приложения. Если бизнес требует такую связь, нужно явно сопоставить её с ID рабочей группы или смарт-процесса, определить источник истины и правила доступа. Это не скрытое поведение текущего MVP.
